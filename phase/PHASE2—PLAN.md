# Phase 2：AI 对话系统计划

## 目标

接入可配置的大语言模型，完成文本对话、上下文管理和固定人格控制。

## 范围与边界

- 支持 OpenAI Compatible API，并保留本地模型适配边界。
- 提供模型、端点、温度、最大输出等配置管理。
- 实现消息历史、流式输出、取消生成、错误重试和基础人格提示词。
- 不在本阶段实现长期记忆、工具调用、语音或自主任务。

## 前置条件与依赖

- Phase 0 的聊天面板和 Phase 1 的 `THINKING` 等状态可用。
- 明确 API 密钥存储方式；密钥不得进入前端 bundle、日志或版本库。
- 确定默认模型、上下文窗口策略和网络超时上限。

## 实施任务

1. 定义 `ChatMessage`、`Conversation`、`ModelConfig`、`StreamChunk` 和错误类型。
2. 实现 `LLMProvider` 接口及 OpenAI Compatible provider，隔离 HTTP 客户端和供应商字段。
3. 实现会话服务：消息追加、流式 token 合并、取消、重试和上下文裁剪。
4. 实现 Persona 配置：名称、性格、回复风格、行为规则和版本号。
5. 将对话生命周期映射到桌宠状态：请求中为 `THINKING`，输出中为工作/说话状态，结束后恢复。
6. 在设置页提供端点、模型和人格配置，敏感配置使用安全存储适配器。
7. 增加网络失败、限流、超时、无效响应和内容为空的用户可理解提示。

## 建议接口

- `LLMProvider.stream(request, signal)`：支持取消信号，输出标准化 `StreamChunk`。
- `ConversationService.sendMessage(conversationId, content)`：返回可订阅的流和最终消息。
- `PersonaService.getActivePersona()`：返回版本化、已校验的人格配置。
- API 层统一返回 `AppError { code, message, retryable, details? }`，UI 不直接解析供应商错误文本。

## 上下文与人格规则

- 系统人格提示词固定放在消息序列最前，并标记来源版本。
- 用户消息、模型消息和系统消息必须区分存储，禁止把用户文本拼接为系统指令。
- 达到上下文限制时按策略裁剪较早消息，并向日志记录裁剪数量，不记录完整敏感内容。
- 流式消息中断后保存可识别的未完成状态，重新发送不得重复追加同一用户消息。

## 阶段交付物

- 可配置 OpenAI Compatible API 的文本聊天。
- 支持流式输出、取消、重试和模型切换。
- 一个版本化 Persona 配置和可编辑设置页。
- 供应商无关的 LLM 与会话接口。

## 验收标准

- 用户发送消息后能看到流式回复，桌宠状态同步变化。
- 网络错误、超时、限流和取消操作均有稳定 UI 结果，应用不崩溃。
- 切换人格或模型只影响新请求，不破坏历史会话。
- API 密钥在进程日志、构建产物和错误提示中不可见。
- 使用 mock provider 时无需外网即可完成核心测试。

## 测试与验证

- Provider 合约测试：正常流、空流、畸形响应、超时、限流和取消。
- 会话测试：上下文裁剪、重试幂等、流合并、并发发送和错误恢复。
- Persona 测试：默认值、版本升级、非法字段和注入式用户文本隔离。
- 集成测试：聊天 UI、状态机和 mock LLM 全链路。

## 风险与后续入口

- 不同兼容 API 的流格式并不完全一致，必须通过 provider 适配而非污染核心模型。
- 记忆系统将改变上下文来源，Phase 3 应通过 `ContextAssembler` 扩展。
- 工具调用需要新的权限和审批流程，不能仅复用普通文本消息。
